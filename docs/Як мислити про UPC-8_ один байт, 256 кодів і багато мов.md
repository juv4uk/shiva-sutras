# Як мислити про UPC-8: один байт, 256 кодів і багато мов

## Найкоротша відповідь

**8 біт** означають, що один елемент потоку може мати **256 різних значень**:

```text
00000000 = 0x00 = 0
00000001 = 0x01 = 1
...
11111111 = 0xFF = 255
```

Математично це `2⁸ = 256`. Отже, UPC-8 — це формат, де одна базова одиниця займає **один байт**.

Але ключове питання не «на скільки мов вистачить 256 кодів?». Правильне питання таке:

> **Які саме сутності заслуговують на окремий байт, а які мають бути mapping-ами, послідовностями або modifiers?**

## 1. Що саме може означати один code point

Один UPC code point не зобов’язаний означати «літеру». Це можуть бути зовсім різні рівні:

| Рівень | Приклад | Чи варто давати окремий byte? |
|---|---|---|
| Графема | `к`, `k`, `q`, `kh` | Не завжди: різні писемності можуть позначати той самий сегмент. |
| Фонема | `/k/`, `/ʃ/`, `/θ/` | Часто так, якщо це atomic contrast у твоєму universal inventory. |
| Фонетична реалізація | `[k]`, `[kʰ]`, `[k̚]` | Не завжди: інколи це base segment + feature/modifier. |
| Складний segment | affricate `/d͡ʒ/` | Залежить від design: один code або sequence `/d/ + /ʒ/`. |
| Просодична ознака | довгота, tone, nasalisation, stress | Часто краще modifier або окремий annotation layer. |
| Контекстне правило | English `th` → `/θ/` або `/ð/` | Ні: це робота language profile / tokenizer, не byte table. |

Тобто byte — це не «символ алфавіту». Byte — це **атом твого формального фонологічного representation**.

## 2. Чому розподіл «одна мова = свій діапазон» швидко вичерпує простір

Поточний UPC-8 prototype уже має:

| Діапазон | Призначення | Кількість |
|---|---|---:|
| `0x00–0x29` | Базові Śiva Sūtras sounds | 42 |
| `0x2A–0x30` | Sanskrit extensions | 7 |
| `0x31–0x4F` | Ukrainian new units | 31 |
| — | Ukrainian shared units | 13, без нових bytes |
| **Усього assigned** |  | **80** |
| **Вільно** |  | **176** |

Якщо далі сказати «English отримує 48 bytes, Polish — ще 35, German — ще 30», простір справді стане тісним. Проблема не в тому, що 256 — мале число. Проблема в тому, що такий design **дублює один і той самий segment** під різними мовними іменами.

Наприклад, не має сенсу зберігати різні bytes для українського `/k/`, польського `/k/`, німецького `/k/` і латинської літери `k`, якщо в обраному phonemic model це один і той самий segment. Мови мають посилатися на спільний byte, а не отримувати власну копію.

```text
Погано:
  Ukrainian /k/ → 0x25
  English   /k/ → 0x74
  Polish    /k/ → 0x91

Краще:
  universal /k/ → 0x25

  ukr profile: «к» → [0x25]
  eng profile: «k», «c», «ck», «ch» in some contexts → [0x25]
  pol profile: «k» → [0x25]
```

Тоді додавання мови майже не витрачає byte space. Воно додає **profile**, тобто mapping rules and metadata.

## 3. Universal inventory і language profile — два різні шари

Найздоровіша архітектура для UPC-8 виглядає так:

```text
          ┌────────────────────────────┐
          │ UPC-8 universal inventory  │
          │ 0x00 → segment A           │
          │ 0x01 → segment B           │
          │ ...                        │
          └─────────────┬──────────────┘
                        │
            ┌───────────┼───────────┐
            ▼           ▼           ▼
       Sanskrit      Ukrainian    English
        profile       profile      profile
       input rules   input rules  input rules
       output rules  output rules output rules
```

### Universal inventory

Це відповідає на питання: **які atomic segments система вміє розрізняти?**

У ньому можуть бути, наприклад:

```text
/a/  /i/  /u/  /k/  /g/  /p/  /m/  /s/  /ʃ/  /r/
/kʰ/ /t͡ʃ/ /d͡ʒ/ /θ/ /ð/ /ɲ/ /ŋ/ ...
```

Важливо: це не обов’язково «IPA у byte form». IPA дуже велика, а твій inventory має бути свідомо обмеженим, versioned і пов’язаним із формальною моделлю.

### Language profile

Profile відповідає на інші питання:

- як конкретна мова пише або вводить segment;
- які segmentation rules застосувати;
- які variants є allophones, а які contrastive phonemes;
- як decode-ити code sequence у потрібній orthography;
- який normalization form використано;
- на яке джерело/registry спирається mapping.

Концептуальний приклад профілю:

```yaml
profile_id: ukr-phonemic-v1
inventory_version: upc8-v0.2
input_mode: orthographic
normalization: NFC

encode:
  "к": [0x25]
  "ш": [0x3B]
  "дж": [0x38]
  "ль": [0x49]

# Це не приклад чинної реалізації — лише потрібна форма контракту.
```

Додавання польського або англійського profile тоді не означає «виділити 40 нових bytes». Воно означає: reuse everything that already exists, а новий byte allocate лише тоді, коли profile знаходить **справді відсутній atomic contrast**.

## 4. Скільки мов реально може працювати з одним 8-bit inventory

Тут є дві різні відповіді.

### Якщо кожній мові віддавати окремий діапазон

Після нинішніх 80 assigned code points вільно 176. За простого припущення, що мові потрібно 20–50 нових, неshared units, це кілька мов:

| Середня кількість нових units на мову | Теоретично вміститься у 176 вільних slots |
|---:|---:|
| 20 | 8 мов |
| 25 | 7 мов |
| 30 | 5 мов |
| 35 | 5 мов |
| 40 | 4 мови |
| 50 | 3 мови |

Це не дуже масштабована модель.

### Якщо мови — це profiles над спільним inventory

Тоді одна й та сама 256-unit система може підтримувати **десятки або сотні мовних профілів**, тому що profile — це data/rules, а не new byte range.

Але це не означає, що 256 unit достатньо для абсолютно всіх фонетичних систем світу в будь-якій деталізації. Швидко з’являються:

- clicks;
- ejectives and implosives;
- багато vowel qualities;
- contrastive length;
- tones/register;
- pharyngeals and uvulars;
- nasalisation, aspiration, labialisation;
- contour tones and coarticulated segments.

Тож 8 біт добре працюють як **base segment layer**, але не як гарантія «один byte покриє будь-який звук людської мови без контексту».

## 5. Як не роздувати inventory: sequences і modifiers

Тобі не треба мати окремий byte для кожної комбінації властивостей. Частину треба виражати послідовністю.

```text
base segment + modifier

/a/ + LONG
/a/ + NASAL
/k/ + ASPIRATED
/n/ + PALATALIZED
```

Це дає можливість зберегти small base inventory. Концептуально можна лишити частину простору для modifiers:

```text
0x00–0x7F   base segment inventory
0x80–0xBF   additional / rare segments
0xC0–0xDF   modifiers and prosody
0xE0–0xEF   control or profile-local extension
0xF0–0xFF   escape, version, future expansion
```

Це **не пропозиція негайно змінити поточні UPC-8 assignments**. Це пояснення принципу. Нинішня layout уже має цінність як історичний experimental artifact; зміна layout без version break лише створить ambiguity.

У майбутньому можна мати два різні формати:

| Формат | Для чого він | Що оптимізує |
|---|---|---|
| **Interchange format** | Читабельний і stable обмін між tools | Versioning, provenance, lossless semantic identity. |
| **Execution format** | FPGA або fast classifier | Bitmap/LUT layout, feature masks, timing. |
| **Storage format** | Файли, corpus, transport | Compression and compactness. |

Це добре збігається з ідеєю, яка вже записана у UPC documentation: не змушувати один byte layout одночасно бути історичним reference, hardware bitfield та compressed storage representation.

## 6. Чому Śiva Sūtras не повинні автоматично диктувати весь universal inventory

Śiva Sūtras можуть бути чудовим **ordered base layer**. Вони дають компактну систему посилань, natural classes через pratyāhāra і історично/формально важливу структуру. Але з цього не випливає, що вони вже є complete universal phoneme inventory або що їхній порядок оптимальний для бітових mask tests.

Тому architecture має зберігати такі твердження окремо:

| Твердження | Статус, який можна мати |
|---|---|
| Śiva Sūtras задають ordered base layer для UPC experiment | Engineering design decision. |
| Певні language segments можна reuse-ити з base layer | Profile-specific linguistic mapping. |
| Specific FPGA bitmap lookup має потрібні resources/timing | Measured engineering result. |
| Śiva Sūtras історично задумувалися як universal code або hardware design | Окреме історичне твердження, яке не випливає з кодування. |

Таке розділення не послаблює задум. Воно дозволяє йому рости чесно: кожен новий результат отримує саме той рівень доказу, який реально має.

## 7. Що я б зробив практично, не ламаючи твою ідею

Перш за все, я б не розподіляв `0x50–0x7F` «під English» наперед. English profile може виявитися mostly reuse existing segments plus a small set of additions. Передчасний contiguous range створює відчуття, що codes належать мовам, а не segments.

Далі я б визначив чотири contracts:

```text
1. UPC assignment contract
   Який code відповідає якому segment ID і яка версія assignment.

2. Canon/source contract
   На яку версію Śiva Sūtras / registry спирається assignment.

3. Language profile contract
   Як конкретна мова tokenise-иться, encode-иться та decode-иться.

4. Execution contract
   Як profile/inventory materialize-иться в FPGA ROM, bitmap або LUT.
```

Після цього можна рухатися малими кроками:

1. Виправити general `pratyāhāra` і зробити exhaustive reference test.
2. Назвати поточний UPC-8 `experimental engineering assignment`, а не universal finished standard.
3. Визначити, чи Ukrainian profile є orthographic, phonemic або transliteration-based.
4. Додати один language profile, який максимально reuse-ить existing inventory, наприклад English або Polish, **без виділення діапазону наперед**.
5. Порахувати actual new contrasts; лише вони отримують нові codes.
6. Окремо generated bitmap tables протестувати на FPGA як independent engineering experiment.

## Фінальна формула

> **8 біт — це не “256 мов” і не “256 літер”. Це 256 стабільних атомів у твоєму representation. Мов може бути багато, якщо вони є profiles над спільними атомами.**

У твоєму випадку найсильніша версія UPC не та, де кожна мова отримує власний block. Найсильніша версія — та, де Śiva Sūtras дають compact ordered root, а language profiles показують, як різні живі системи частково reuse-ять, частково розширюють і ніколи не плутають цей root зі своїм власним письмом чи фонетичною surface form.
